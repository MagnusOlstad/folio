# Entity extraction jobs

`createEntityJobService(capturedRuntime)` is the per-bundle internal trigger and durable queue. The runtime is captured at construction and every request must repeat its `bundleId`; request text and hashes are never accepted from callers. Note IDs are validated through that runtime's `resolveBundleMarkdownPath`, including Folio's leading-slash IDs.

The service exposes `initialize()` (also `recover()`), `requestEntityExtraction({bundleId,noteIds?,reason,force?})`, `listJobs({limit?,cursor?})`, `getJob(id)`, `pauseJob(id)`, `resumeJob(id)`, `cancelJob(id)`, `invalidateNotes(noteIds,reason?)`, `snapshot()`, and `close()`. The reason is one of `save`, `capture`, `import`, `transcription`, `ocr`, `enablement`, `startup`, `rebuild`, `history-restore`, `manual`, or `move`. Omitting `noteIds` performs a bundle backfill from indexed note IDs. `force` bypasses valid-result reuse and generation suppression.

The HTTP API is bundle-scoped through `x-folio-bundle`:

- `POST /api/entities/jobs` accepts `{ noteIds?, force?, reason? }` and returns `202` with a persisted job.
- `GET /api/entities/jobs?cursor=&limit=` returns a deterministic page, bundle mode, and any backfill admission error.
- `GET /api/entities/jobs/:jobId` reads a job from that bundle only.
- `POST /api/entities/jobs/:jobId/{pause,resume,cancel}` controls persisted work.

Job data is stored atomically as `entity-jobs.json` beside the bundle's search index. It stores bounded task metadata, source generations and hashes, but never note text. In-flight work returns to the queue on restart; result coverage is checked against the exact projection and fingerprint, so successful empty results are reusable. A damaged job file is left untouched and fails consistently with an actionable `ENTITY_JOB_STORAGE_INVALID` error; preserve it and quarantine/remove it before rebuilding the queue from notes. The current job state cap is 16 MiB, 2,000 retained jobs, and 10,000 pending note tasks; limits fail explicitly.

The worker reads raw Markdown through the captured runtime, parses its body and applies the same `indexedConceptContent` normalization used by search, then projects the body with `projectMarkdown`. The fingerprint pins model ID/revision, native schema, projection version, preprocessing version, and a hash of labels, thresholds, token budget, and overlap. Model planning must cover the whole projection without gaps and remain within 512 tokens including schema tokens. Extraction is one bounded chunk per helper call; the worker yields between chunks and deduplicates exact typed spans from overlap. Structural span errors fail the item. Valid mentions below their type threshold are filtered. A valid empty extraction commits complete coverage.

Inference runs outside Markdown/index locks. Before each chunk, the engine checks `mlxService.getEntityModelStatus()` and distinguishes disabled, missing model, unavailable platform, and unavailable helper pauses. After inference it rereads the source and calls `replaceNoteMentions` with `contentHash`, `extractionFingerprint`, and `expectedSourceGeneration`; the foundation service compares that generation again inside its Markdown mutation guard before committing.

Repeated requests for the same current note generation share one task. A newer generation aborts/supersedes active work; stale results never become coverage. Explicit manual pause and cancellation suppress automatic requests for that captured generation across restart; resume or an explicit forced/rebuild request clears the suppression. Retries are limited to four attempts with exponential backoff capped at 30 seconds. Missing assets, disabled preferences, helper failure, source changes, and cancellation retain distinct actionable job-item states.

Committed saves, captures, imports, history restores, and moves enqueue extraction without waiting for native inference. Automatic triggers skip job admission while analysis is disabled; explicit job requests remain paused with a visible explanation. Deletion and path moves invalidate pending work and update durable note locators after the Markdown mutation completes. The service subscribes to `entityService.onAnalysisSettingsChange` and `mlxService.onEntityModelAvailabilityChange`; enabling analysis or installing the model triggers backfill. Removing the model pauses work and retains the bundle preference. A persistence failure switches the service snapshot to `storage_error`, includes a bounded diagnostic, aborts active extraction, and stops admission; detached lifecycle and pump callbacks contain their rejected promises. Startup integrations contain entity metadata/job recovery errors so note browsing remains available and entity endpoints show an actionable `503` rather than resetting damaged state.
