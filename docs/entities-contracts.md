# Entity contracts

Entity APIs are additive and use the active bundle selected by `x-folio-bundle` (or the existing default-bundle rule). There is no bundle ID in request bodies. Each bundle's `entity-index.json` and `entity-user-state.json` live beside its configured `search-index.json`; this keeps legacy, named, and pending bundles in their existing isolated app-state roots. The index is rebuildable. A malformed or oversized index is treated as stale and rebuilt. A malformed correction ledger returns HTTP 503 with code `ENTITY_LEDGER_DAMAGED`; it is preserved for recovery and never reset automatically. Both JSON files are limited to 32 MiB and replaced atomically. Writes are serialized per bundle.

`GET /api/entities?q=&type=&cursor=&limit=` returns `{items,nextCursor,revision,indexRevision,stale,coverage}`. `type` is one of `person`, `organization`, `project`, `product`, or `location`. Pages default to 25 and are capped at 100. Items sort by preferred label and then stable ID. Cursors are base64url-encoded offsets in that order. Coverage counts source notes as `{eligible,processed,stale,failed,pending}`. Entity `noteCount` is distinct source notes; `mentionCount` is explicitly an occurrence count.

`GET /api/entities/:entityId` returns the entity, its distinct current `noteIds`, correction `revision`, and explicit `noteLinks`. `GET /api/entities/:entityId/mentions?cursor=&limit=` returns `{items,nextCursor,indexRevision}` in descending note-date order, then note ID and display-span order; items include a current note title/date and source excerpt when readable. `GET /api/entities/mentions?noteId=&includeDismissed=true` returns `{items,staleCount,freshness,coverage}` for the current note; dismissed mentions are omitted unless explicitly requested. Stale and deleted-note occurrences are excluded from entity counts, details, and mention pages. `contentHash` is the hash of the current user-visible note content used for freshness checks.

Mention `startUtf16`/`endUtf16` are zero-based half-open UTF-16 offsets into the versioned extraction projection. YAML frontmatter, generated-related sections, and synthetic capture wrapper lines are excluded from that projection. `rawStartUtf16`/`rawEndUtf16` map the verified span into the normalized Markdown body after frontmatter and generated wrapper handling; `displayStartUtf16`/`displayEndUtf16` map it into the note body returned to workspace editors. The service validates the projected substring and the mapped source substring against the model text before storing a mention. `extractionFingerprint.inputHash` hashes the exact projection; `contentHash` fingerprints the current body read from the Markdown file, never a potentially stale search-index record. The file's size and modification generation let paginated list/detail calls suppress stale mentions with bounded concurrent `stat` reads; those calls do not load every note body. The current-note mentions route reads and validates only that note's body. A user edit makes the old occurrence stale until a current extraction is committed.

`POST /api/entities/corrections` accepts `{expectedRevision,command}` and returns `{revision,indexRevision,undoToken}`. A revision mismatch returns HTTP 409 `REVISION_CONFLICT` without changing either file. A durable correction record stores `id`, `bundleId`, `expectedCorrectionRevision`, `revision`, the validated command, its `scope`, inverse data, and `undoToken`. The index records the correction revision it has applied. If a crash occurs after the ledger is written but before the index, the next read replays the durable per-mention decisions in memory and the next mutation persists the repaired index. Commands are:

```json
{"type":"rename","entityId":"ent-id","label":"Preferred label"}
{"type":"retype","entityId":"ent-id","entityType":"organization"}
{"type":"add-alias","entityId":"ent-id","alias":"Confirmed alias"}
{"type":"remove-alias","entityId":"ent-id","alias":"Confirmed alias"}
{"type":"merge","entityId":"ent-source","targetEntityId":"ent-target"}
{"type":"split","entityId":"ent-source","mentionIds":["men-id"],"label":"Distinct identity"}
{"type":"reassign","mentionIds":["men-id"],"entityId":"ent-target"}
{"type":"dismiss","mentionIds":["men-id"]}
{"type":"restore","mentionIds":["men-id"]}
{"type":"do-not-merge","leftEntityId":"ent-a","rightEntityId":"ent-b"}
{"type":"link-note","entityId":"ent-id","noteId":"/notes/example.md"}
{"type":"unlink-note","entityId":"ent-id","noteId":"/notes/example.md"}
```

`POST /api/entities/corrections/undo` accepts `{expectedRevision,undoToken}`. `GET /api/entities/corrections/latest` returns the newest correction's undo state. Only the newest correction can be undone; the undo token and inverse state are durable, and undo after restart returns HTTP 409 if a later correction has already superseded it. Commands and undo are bundle-wide; mention assignment/dismissal commands identify occurrences by stable bundle-local mention IDs. Renames, aliases, links, type changes, merge/split, and do-not-merge decisions are bundle-local. `dismiss-related` suppresses one co-mention suggestion for a source note and can be undone through the same latest-correction endpoint. `GET /api/entities/related?noteId=` returns paged co-mention suggestions, omitting dismissed suggestions and explicit Markdown links.

Extracted mention fields and identity resolution are separate concepts: the index exposes their combined read view, while durable `mentionDecisions` in the user ledger own user assignments, dismissals, corrected types, and source-locator IDs. A resolution records `mentionId`, `entityId`, `resolved|unresolved|ambiguous` status, and `model|rule|user` provenance. Automatic identity resolution groups exact normalized labels for non-person types. Person mentions get occurrence-local identities so identical display names do not imply the same person. A single-token person mention remains ambiguous; confirmed aliases and explicit user assignments can resolve it. Fuzzy, first-name, and embedding matches never silently combine identities. User mention decisions are stored by stable note/span/text locator and replayed on extraction rebuild.

`GET /api/entities/jobs` returns `{items,nextCursor,mode}`; coverage is reported by entity listing, not the jobs response. `POST /api/entities/jobs` admits extraction work and returns HTTP 202. Job detail routes support pause, resume, and cancel. Corrupt `entity-jobs.json` remains byte-for-byte in place and returns a sticky HTTP 503 until an operator preserves then removes or quarantines that file; the queue is not automatically rebuilt while it is damaged.

`GET /api/entities/metadata` exports versioned user state. `POST /api/entities/metadata` imports that attachment into the active bundle, preserving stable IDs and user decisions while clearing the derived index so it can be rebuilt from that bundle's notes. The import endpoint accepts a bounded 34 MiB JSON envelope so the 32 MiB state limit can round-trip with its version and bundle metadata. Correction history is never silently truncated; a write that would exceed 32 MiB fails explicitly. Folio ZIP backups include the attachment at `bundles/<name>/.folio/entity-metadata.json`; when a restored bundle is attached, Folio imports it only into an empty ledger, then rebuilds derived mentions as extraction runs. This path is excluded from the bundle's normal Markdown tree. A damaged ledger blocks backup preflight with HTTP 503 and `ENTITY_LEDGER_DAMAGED`, before archive headers are sent. Markdown and OKF exports are unchanged.
